# File

`Assets/Resources/solar_system.json`

The file is generated by `tools/generate_solar_system.py` and loaded at runtime
with Unity's `JsonUtility`. It is checked into the project so the game runs
without a network connection or a Python environment.

A second file, `Assets/Resources/trade_catalogue.json`, holds commodities and
station prices. It is hand-edited, not generated, and loaded through
`TradeCatalogueLoader` ([ADR-020](/decisions/adr-020-trade-catalogue.md)); its
format is below.

# Top level

```json
{
  "name": "Time to Explore - Sol",
  "epochUtc": "2026-11-15T00:00:00Z",
  "epochJulianDate": 2461359.5,
  "startJulianDate": 2461359.5,
  "sourceNote": "…",
  "bodies": [ … ]
}
```

| Field | Type | Meaning |
|---|---|---|
| `name` | string | Display name of the catalogue |
| `epochUtc` | string | Human-readable epoch |
| `epochJulianDate` | number | Julian date of the catalogue epoch |
| `startJulianDate` | number | Julian date at which the game starts |
| `sourceNote` | string | Provenance summary |
| `bodies` | array | All bodies; order does not matter |

# Body

```json
{
  "id": "earth",
  "name": "Earth",
  "kind": "planet",
  "parent": "sun",
  "radiusM": 6371000.0,
  "gm": 398600441800000.0,
  "rotationPeriodS": 86164.2,
  "axialTiltDeg": 23.44,
  "poleRaDeg": 0.0,
  "poleDecDeg": 90.0,
  "color": [0.2, 0.42, 0.72],
  "description": "Home world…",
  "albedoTexture": "Planets/earth_albedo",
  "atmosphere": {
    "heightM": 100000.0,
    "color": [0.35, 0.56, 1.0],
    "intensity": 1.1
  },
  "orbit": {
    "aM": 149598487062.6,
    "e": 0.016699,
    "iDeg": -0.003494,
    "raanDeg": 0.0,
    "argPeriDeg": 103.025,
    "meanAnomalyDeg": -49.299,
    "epochJulianDate": 2461359.5,
    "plane": "ecliptic"
  },
  "lagrange": null
}
```

| Field | Type | Units | Meaning |
|---|---|---|---|
| `id` | string | — | Unique stable key, lowercase snake_case |
| `name` | string | — | Display name |
| `kind` | string | — | `star`, `planet`, `moon`, `asteroid`, `station` |
| `parent` | string or null | — | Parent body id; null only for the Sun |
| `radiusM` | number | m | Mean radius |
| `gm` | number | m³/s² | Gravitational parameter |
| `rotationPeriodS` | number | s | Sidereal rotation; negative = retrograde |
| `axialTiltDeg` | number | ° | Obliquity to the orbital plane |
| `poleRaDeg` | number | ° | IAU north pole right ascension (J2000) |
| `poleDecDeg` | number | ° | IAU north pole declination (J2000) |
| `color` | array of 3 numbers | 0–1 | Placeholder RGB |
| `description` | string | — | One-line catalogue note |
| `albedoTexture` | string or null | — | Resources key of the albedo map; null when the body has none |
| `atmosphere` | object or null | — | Visible-atmosphere tint; null for an airless body |
| `orbit` | object or null | — | Keplerian elements; null for the Sun and stations |
| `lagrange` | object or null | — | Station configuration; null for everything else |

# Appearance

Two optional fields carry the first art pass. Both are emitted for every body,
with `null` where they do not apply, so a reader never has to tell a missing key
from an absent feature.

* `albedoTexture` is a Unity **Resources** key under
  `Assets/Resources`, not an asset path. The convention is
  `Planets/<id>_albedo`, and the file on disk is either
  `Assets/Resources/Planets/<id>_albedo.jpg` or `.png`. The eight planets and
  Earth's Moon have one; the Sun, the other 21 moons, the asteroids and the
  stations have `null`.
* `atmosphere` is the visible-atmosphere shell the renderer will draw in a later
  step, or `null` for an airless body. `heightM` is the real height above the
  surface in metres, `color` is the authored **sRGB** tint (three numbers in
  [0, 1]), and `intensity` scales the rim in (0, 2]. Heights are real, not
  inflated for looks: Earth is 100 km, and `heightM` must stay below 6% of
  `radiusM` so the shell never swallows the body.

```json
"albedoTexture": "Planets/mars_albedo",
"atmosphere": { "heightM": 120000.0, "color": [0.88, 0.62, 0.45], "intensity": 0.8 }
```

The catalogue colour stays the flat marker tint. The albedo map replaces it only
when the renderer's detail gate is open, so a distant body is still a cheap
coloured marker. The maps are equirectangular, sRGB-imported colour textures;
the import settings are pinned by `Assets/Editor/PlanetTextureImporter.cs`. See
[Planet appearance](/technical/planet-appearance.md) for the pipeline and the
attribution.

The two fields are data only at this point: the textured body shader and the
atmosphere shell are later steps.

`JsonUtility` does not keep a null nested object. In the runtime model
`atmosphere` is never null: a `null` in the file arrives as a default
`AtmosphereData` with `heightM` 0. Ask `BodyData.HasAtmosphere`, which tests the
height, rather than testing the object for null.


# Orbit

| Field | Type | Units | Meaning |
|---|---|---|---|
| `aM` | number | m | Semi-major axis |
| `e` | number | — | Eccentricity |
| `iDeg` | number | ° | Inclination to the reference plane |
| `raanDeg` | number | ° | Longitude of ascending node |
| `argPeriDeg` | number | ° | Argument of periapsis |
| `meanAnomalyDeg` | number | ° | Mean anomaly at `epochJulianDate` |
| `epochJulianDate` | number | JD | Epoch of the elements |
| `plane` | string | — | `ecliptic` or `parentEquator` |

For a planet or asteroid, the parent is the Sun and `plane` is `ecliptic`.
For a moon, the parent is the planet; `plane` is `parentEquator` for most moons
and `ecliptic` for Earth's Moon. The parent's `GM` supplies the gravitational
parameter, so the orbit's period is derived from `aM` and `GM`, not stored.

# Lagrange station

```json
"lagrange": { "primary": "earth", "secondary": "moon", "point": "L1" }
```

| Field | Type | Meaning |
|---|---|---|
| `primary` | string | More massive body id |
| `secondary` | string | Less massive body id |
| `point` | string | `L1`, `L2`, `L4`, or `L5` |

A station also has a `parent` (normally the secondary) so the hierarchy and
nearest-body queries work. Its position is not derived from `parent`; it is
recomputed each frame from the pair.

# Units summary

* lengths: metres in the file (semi-major axes are converted from AU at
  generation time),
* `GM`: m³/s²,
* time: seconds for periods, Julian date for epochs,
* angles: degrees in the file, radians in the runtime.

# Generation

```bash
# regenerate everything (downloads asteroid data on first run)
python3 tools/generate_solar_system.py

# reuse tools/cache/asteroids.json, useful offline
python3 tools/generate_solar_system.py --offline
```

The script:

1. Evaluates the JPL planet elements and rates at the game epoch.
2. Builds the Sun, planets, and major moons from the tables in the script.
3. Downloads (or reuses) the 100 largest main-belt asteroids from JPL SBDB.
4. Advances each asteroid's mean anomaly to the common epoch.
5. Adds the six station definitions.
6. Writes the JSON and reports the body count.

The asteroid response is cached at `tools/cache/asteroids.json`; the field list
is cached alongside it. The cache is generated data and can be deleted safely.

# Adding a body

## A moon

Add an entry to `MOONS` in the generator:

```python
dict(id="moon_id", name="Moon Name", parent="planet_id",
     a_km=123456.0, e=0.001, i=0.5, radius_km=123.4,
     gm=1.0e10, period_d=1.234, color=[0.6, 0.6, 0.6],
     description="…"),
```

`period_d` is used to derive a consistency check for `GM`; the runtime derives
the actual period from `parent.gm` and `a_km`. Keep them close.

## A station

Add to `STATIONS`:

```python
dict(id="station_id", name="Station Name", primary="sun", secondary="earth",
     point="L2", size_km=2.0, description="…"),
```

## A planet or a large asteroid with fixed elements

If you do not need the JPL mean-element fit, add a body directly to `bodies` in
the generator with an `orbit` block. If you do, extend `PLANETS` with the
six-element tuple and rates; the format is documented in the script.

# Validation checklist

Run `tools/check.sh --fast` (or `python3 tools/validate_catalogue.py`) to
enforce the list below; the Unity EditMode suite repeats the runtime half.

Before committing a regenerated catalogue:

* Every `parent` resolves to an existing body.
* Every `id` is unique.
* Every display name is unique. Asteroid names that collide with a moon
  (52 Europa, 85 Io, 106 Dione) are number-qualified by the generator.
* The Sun is the only body with `parent: null`.
* `gm > 0` for every gravitating body; stations may be zero.
* A body with `orbit` has a positive `aM`, `0 ≤ e < 1`, and a finite epoch.
* `albedoTexture` is null or matches `Planets/[a-z0-9_]+`, and a `.jpg` or
  `.png` exists under `Assets/Resources` for every key that is set.
* The eight planets and the Moon have an albedo texture; no asteroid or station
  does.
* `atmosphere` is null or has `heightM` in (0, 6% of `radiusM`), a `color` of
  exactly three numbers in [0, 1], and `intensity` in (0, 2].
* A moon's `aM` is inside its parent's Hill sphere.
* A station's `primary` and `secondary` both exist.
* `startJulianDate` equals the epoch used by the elements.
* The body count is 137 for the shipped catalogue (1 + 8 + 22 + 100 + 6).

The Unity importer will regenerate `.meta` files on first open. If the JSON is
replaced while the editor is running, focus the editor or reimport the asset.

# Trade catalogue

`Assets/Resources/trade_catalogue.json` is the economy's content. It is
separate from the orbital catalogue so prices can change without regenerating
137 bodies, and it is hand-edited: no Python tool writes it.

```json
{
  "commodities": [
    { "id": "water", "name": "Water", "volumePerUnitM3": 1.0,
      "massPerUnitKg": 1000.0, "description": "Potable water and coolant." }
  ],
  "markets": [
    { "stationId": "gateway", "offers": [
        { "commodityId": "water", "buyPrice": 8, "sellPrice": 6 }
    ] }
  ]
}
```

| Field | Type | Meaning |
|---|---|---|
| `commodities` | array | Every tradable good; ids are unique |
| `commodities[].id` | string | Stable key, lowercase snake_case |
| `commodities[].name` | string | Display name |
| `commodities[].volumePerUnitM3` | number | Cargo volume one unit takes |
| `commodities[].massPerUnitKg` | number | Mass one unit adds; displayed only for now |
| `commodities[].description` | string | One line for the panel |
| `markets` | array | One entry per trading entity |
| `markets[].stationId` | string | Body id; a station or a planet. The name is historical |
| `markets[].offers` | array | Commodities this entity trades; may be a subset |
| `offers[].commodityId` | string | Existing commodity id |
| `offers[].buyPrice` | integer | What the station charges the player |
| `offers[].sellPrice` | integer | What the station pays the player |

`buyPrice` must be at least `sellPrice`; a station that pays more than it
charges is free money and a data error. Prices are labels in the first pass: a
transaction moves whole units and charges nothing
([Trade](/world/trade.md)).

# Validating trade data

`tools/validate_trade.py` is the fast gate. It runs in `tools/check.sh` and
`tools/check.sh --fast` as the step after the orbital catalogue, reads the trade
file and `solar_system.json`, and prints one `FAIL` line per problem:

* every `commodityId` resolves to a shipped commodity,
* every `markets[].stationId` resolves to a body in `solar_system.json`,
* every commodity id and every market station id is unique,
* `volumePerUnitM3 > 0` and `massPerUnitKg > 0`,
* no market lists the same commodity twice,
* `buyPrice >= sellPrice >= 0`, and both prices are integers,
* at least one market offers each shipped commodity, so no good is dead content.

`TradeCatalogue.Parse` enforces the file's own schema when the asset loads and
throws an `InvalidOperationException` naming the offending row. The cross-file
rule stays in the validator, because `Core` does not load the orbital catalogue.
`TradeCatalogueTests` (category `core`) pins the same rules through the runtime
path, and `tools/test_validate_trade.py` covers the validator itself.

# Why JsonUtility

Unity's built-in `JsonUtility` handles arrays inside a root object, nested
serializable classes, and `double` fields. It does not handle dictionaries or
top-level arrays. The schema is shaped around those limits so the project needs
no third-party JSON dependency.

If the catalogue grows to the point where streaming, schema validation, or
dictionary lookups matter, a custom reader or Newtonsoft JSON is a reasonable
upgrade. For 137 bodies, the built-in parser is more than sufficient.
